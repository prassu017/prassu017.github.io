Agent orchestration01

44% → 100% exact-value accuracy

A conductor that only ships verified values

Context
A single agent filling client documents emitted wrong numbers with full confidence, and nothing in the system knew which outputs were wrong.
My call
Designed a contract-driven multi-agent orchestrator. A conductor compiles a per-workflow contract into dependency-ordered waves of steps; sub-agents run with scoped tools (caller permissions ∩ step scope ∩ read-only), an inline verify gate checks every step and can trigger a repair, state lives in durable Temporal workflows, and budgets are hard-capped. A value only leaves the system if two independent resolutions agree. Otherwise it's withheld and the field is named.
Proof
Against the single-agent baseline on real client data: exact values 44% → 100%, worst delivered error −$1,000,001 → $0, repeat runs from 0 of 4 clients agreeing to byte-identical, at about $0.34 and 90 seconds per fully audited client run.

Field note: don't ask the model to be right. Build a system that can't deliver wrong.

Verification02

0 false passes in production

A probe the agent can't influence

Context
An eval that reads the agent's own transcript inherits the agent's mistakes.
My call
Built a transcript-blind probe that re-fetches every value from the system of record in a fresh session, then a three-way per-field comparison: filled, retrieved and probed. A run counts as proven only when it has real field verdicts, never on an empty "pass".
Proof
First production batch: 24 field verdicts, 4 passes, 20 honest catches, 0 false passes, across a 126-field contract.

Field note: a check that only observes isn't a gate.

Customer escalation03

$10M+ in balances restored

The silent feed

Context
A client reported missing values. No alert had fired, the job said success, and every dashboard was green.
My call
Traced records from our database to the data provider's feed and found an account code never registered on their side. Then audited history: 12 of 122 days missed, silently. Registered the missing accounts and added freshness monitoring.
Proof
376 accounts and $10M+ in balances flowing again the next business day, 19% of that client's book.

Field note: "the job ran" and "the data is current" are different things.

Distributed systems04

1× per action, even on retry

Retries that never double-send

Context
Durable workflows retry and restart, and an agent that emails a client or writes to a CRM twice is a real incident.
My call
Keyed every external write by hash(workflow run, step, normalized operation) and claimed it with an atomic INSERT … ON CONFLICT DO NOTHING. If the claim store is unreachable, the write is withheld, not risked.
Proof
At-most-once external writes across Temporal retries and worker restarts, failing closed by design.

Field note: idempotency is a product feature, not plumbing.

Reliability05

20-run replay harness

Determinism you can prove

Context
The same workflow gave different answers on identical inputs: a total changed format, drifted, or came back blank.
My call
Moved exact values out of the prompt into a deterministic rule layer, then built a harness that replays a task 20 times and diffs every output.
Proof
It caught a $380.96 vs $381 drift, and a fix that passed its unit tests but never fired in a live run.

Field note: fix determinism in code, not in prompts.

Production cutover06

500 PRs → 5 stacked releases

Shipping a new engine under live customers

Context
Staging and main had drifted by 692 files and about 500 PRs, with roughly 82k lines that had never run in CI, while customers used the system every day.
My call
Split it into 5 stacked, reviewable PRs, turned CI on across all of it, sequenced 13 schema migrations so no deploy could break writes fleet-wide, and proved the kill switch and org allowlist with live runs before relying on them.
Proof
Cut over to production without disrupting a single customer workflow.

Field note: make risky changes small, reviewable and reversible.

Field notes

What deployments taught me

Each of these came from something that broke, or almost did, in front of a customer.

01

A check that only observes isn't a gate

If a result can't be proven against the source, it's held back. A confident wrong answer in front of a customer is worse than no answer.

02

Measure the measurer

I once saw a model that had stopped responding score as a slightly weak one. Evaluation needs its own failure modes tested.

03

Fix it in code, not the prompt

Values that must be exact belong in deterministic code. Consistency only became provable once the logic left the prompt and a 20-run replay agreed.

04

Green dashboards can lie

The job ran and the data is current are different things. Monitor what the customer actually cares about, not what the system says about itself.
